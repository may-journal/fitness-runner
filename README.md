# fitness

Zero-dependency Go fitness runner. It runs checks for local dev, CI/CD, and GenAI workflows to keep code aligned with your rules and quality bar.

Every check is its own static binary (`fitness-check-<name>`), orchestrated by a `fitness` runner binary. No runtime dependencies, no build step for consumers, instant startup, parallel execution. The full suite this repo gates its own commits on runs in about 100 milliseconds. The original TypeScript implementation has been retired, its checks ported one at a time with side-by-side parity (see the Go-rewrite plan, issue #51).

## Install

<!-- cspell:ignore xzf -->

### Go toolchain

For consumers who choose source builds:

```bash
go install github.com/may-journal/fitness-runner/go/cmd/...@v1
```

One command installs `fitness`, the installer and the release tools into `$HOME/go/bin`; put that directory on PATH. Its first run installs the checks the repo pins, verified, into your cache. Upgrade by rerunning with `@v1`.

### Prebuilt binaries

Download the compiled Go installer for your platform from [the releases page](https://github.com/may-journal/fitness-runner/releases). It fetches and checks the full binary bundle, with no Go toolchain on the consumer machine.

The checks install separately, as [install checks](docs/ci.md#install-checks) explains. The [complete setup guide](docs/ci.md) gives exact download URLs and commands for hooks, Jenkins, and Actions. The installer, hook, and release tools are Go executables; no shell installer is shipped.

### From source

For contributors:

```bash
git clone https://github.com/may-journal/fitness-runner && cd fitness-runner
cd go && mkdir -p bin && go build -o bin ./cmd/...
```

Put `go/bin` on PATH, or copy `fitness` onto it. It runs `local-branch` itself and fetches each other check a repo pins from fitness-checks. The Go toolchain is the only build requirement — no npm, no node.

`fitness --help` prints the same list. The [performance record](docs/ci.md#performance-record) explains `--json`, and the [box diagram](docs/ci.md#box-diagram) explains `boxes`.

On a terminal, a long run names each running check with its elapsed time and limit every five seconds. Off a terminal, it names a check once at half its limit. The summary then names the slowest checks with their times. The last check running streams its output live, as the [check protocol](docs/check-protocol.md#progress) explains.

## Git hooks

In a consumer repo, run `fitness init` once. It points Git at the `.fitness-hooks` folder the repo ships, or else installs the shared hooks as one-line shims in `.githooks`. A hook repairs a clone whose `core.hooksPath` still names an old folder in the repo.

- commit-msg: runs `semantic-commit`, `plan-trailer`, and `issue-link-once` on the message being written.
- pre-commit: checks the staged files, then a repo's own `.githooks/pre-commit.local`. It skips `semantic-commit` when a commit-msg hook will judge the new message.
- pre-push: blocks a push whose open PR closes no approved `Plan` Issue, via `gh`. Chore/docs pushes and branches with no PR pass.

Neither hook runs the full scan a pull request adds, so a red main never blocks a commit or a push. Run `fitness --all` for it locally.

A full run, such as `fitness --all`, has `semantic-commit` judge only the branch's own commits. See [its README](https://github.com/may-journal/fitness-checks/blob/main/cmd/fitness-check-semantic-commit/README.md#which-message-it-judges) for how it finds the base.

## GitHub Actions

Some checks also run as GitHub Actions workflows. They extend the same rules to non-file targets like plan Issues and pull request descriptions. Each workflow step is one `fitness` call. See [.github/workflows/README.md](.github/workflows/README.md).

A pull request runs in two stages. Stage 1 checks the changed files and stops the run when it fails. Stage 2 then scans every file, so a pull request fails while the repo does, and it lists findings outside the change apart.

A huge repo sets `"scopedPullRequests": true` in `.fitnessrc.json` to skip stage 2; a push to main still scans every file. See [pull request stages](docs/check-protocol.md#pull-request-stages).

## Release updates

After main CI passes, Release Please opens or updates a release PR from conventional commits. Merging that PR creates a draft release and a `v1.x` tag. GoReleaser builds and packages four platforms; native and public checks gate promotion to latest. Verification adds a Go module tag and moves the `v1` major tag.

Release PRs use the normal review and checks. See [release automation and recovery](docs/ci.md#release-automation) for App access and retries. Other repos use `@v1` and get each 1.x release without an update PR.

## Go coverage

The optional [Go coverage check](https://github.com/may-journal/fitness-checks/blob/main/cmd/fitness-check-go-test-coverage/README.md) requires full entry coverage and reports gaps down the source tree. It also rejects wrappers that can hide independently measured tests. Run `fitness go-test-coverage --all`.
